# Cutting a pi-rs release

This is the release runbook. It complements `PLAN.md` (P7 exit: "tagged
v0.1.0") and `AGENTS.md` (git/release policy). The installer contract
(`scripts/install.sh`) is defined at the bottom of this document.

## v0.1.0 — actual release state (2026-11-21)

The `v0.1.0` tag was pushed on the green version commit `7bb47d6` and the
GitHub Release was created with **two Linux assets** (`pi-linux-x86_64`,
`pi-linux-aarch64`) plus their `.sha256` files; all checksums verified. The
tag workflow's macOS jobs sat queued indefinitely at the time (no hosted
macOS capacity), so the run was cancelled and the release published with the
two completed Linux artifacts via `gh release create` — the manual fallback
described below.

The repository is now **public** and the release matrix again includes
`macos-13` / `macos-14` and `windows-latest`. If a macOS row is still queued
when a release is cut, publish the available assets manually with
`gh release create` and add Darwin assets later with `gh release upload`.

> **Access note:** `hakergeniusz/pi-rs` is **public**. Release assets are
> anonymously downloadable and `GITHUB_TOKEN` is optional (the installer uses
> the API fallback only when a token is supplied).

## 1. Version discipline

- `main` carries pre-release versions: workspace `0.1.0-alpha.x` (`AGENTS.md`).
- The first stable cut is `v0.1.0`. The tag is `v0.1.0` (with the leading `v`);
  the Cargo version is `0.1.0`.
- Only the coordinator performs the bump, and only after the user approves the
  cut. Never bump on a feature branch as a side effect of other work.

Files that carry the version (rg before and after the bump — `rg -n
'0\.1\.0-alpha' --glob '!Cargo.lock' .`):

| File | Lines (at this writing) | Change |
|---|---|---|
| `Cargo.toml` | 15 | `[workspace.package] version = "0.1.0-alpha.1"` → `"0.1.0"` |
| `Cargo.toml` | 54–60 | the seven `[workspace.dependencies]` internal `version = "0.1.0-alpha.1"` entries → `"0.1.0"` |
| `Cargo.lock` | generated | regenerated by any cargo command during the gate; commit it |
| `README.md` | 7 | `Status: v0.1.0-alpha.1 (pre-alpha)` → `Status: v0.1.0` (and adjust the prose if needed) |

Crate manifests use `version.workspace = true` / `workspace = true`, so they
inherit automatically — no per-crate edits. `AGENTS.md:133` is policy prose
("workspace `0.1.0-alpha.x`") and stays as-is unless the policy itself changes.
`HANDOFF.md` is a dated log: append a new entry, do not rewrite history.

After `v0.1.0`, subsequent patches follow semantic versioning (`v0.1.1`, …) on
`main`, with the tag and Cargo version kept in lockstep.

## 2. Preconditions for the cut

- P7 exit criteria are met: release binary builds, installer + checksums work,
  and the P7 tail items delegated for this milestone have landed (`PLAN.md` §4,
  `AGENTS.md` "Current status").
- The full gate is green **in CI on `main`** (see §4). CI is the authority for
  the full run; the workstation's long local gates get cancelled by restarts.
- This slice's three files (`scripts/install.sh`, `docs/RELEASE.md`,
  `WIRING.md`) are merged, and the workflow diff in `WIRING.md` §2 is applied
  and merged before the tag is pushed — otherwise the tag has no published
  assets for the installer to fetch.
- User has explicitly approved: the version bump, the push, the tag, and the
  GitHub Release creation (`PLAN.md` §7: "No GitHub push until user explicitly
  approves").

## 3. What CI does today

`.github/workflows/ci.yml` runs on every push to `main` and on PRs. Jobs: `fmt`,
`clippy`, `test`, `no-default-features`, `msrv`, `audit` (advisory,
non-blocking), and `release`.

The `release` job (lines 94–113) currently:

1. checks out the repo on `ubuntu-latest` with stable Rust;
2. sets `CARGO_PROFILE_RELEASE_DEBUG: 0` and `CARGO_PROFILE_RELEASE_STRIP:
   symbols` (matching the thin-LTO + stripped `[profile.release]` in
   `Cargo.toml`);
3. runs `cargo build --release`;
4. uploads `target/release/pi` as the **CI artifact** `pi-linux-x86_64`.

That job is a per-push *build smoke test*, not a release publisher. It does
**not** create a GitHub Release, has no checksum generation, and builds only
one of the four targets the installer supports. Those gaps are catalogued and
fixed as a proposed diff in `WIRING.md` §2.

## 4. The full gate

Run all five steps, in this order (`AGENTS.md` "Build and test"; `.gate.sh`):

```sh
cargo fmt --all
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace -- --test-threads=4
cargo fmt --all -- --check
cargo check -p pi-coding-agent --no-default-features   # NDF
```

`NDF` is not redundant: the `pi-ext-js` dependency is optional, and a
cfg-fenced build once went red without any other job noticing. The interactive
tests need `fd` and `rg` on `PATH` (CI apt-installs `ripgrep` + `fd-find`).

On the workstation (memory-capped machine), use the RAM container and let CI
own the full run:

```sh
podman exec pi-rs-build-ram sh /work/scripts/ram-build.sh gate
podman exec pi-rs-build-ram sh /work/scripts/ram-build.sh snapshot
```

Equivalent host gate for a machine with enough RAM:

```sh
CARGO_INCREMENTAL=0 CARGO_PROFILE_DEV_DEBUGINFO=0 sh -c \
  'cargo fmt --all && cargo clippy --workspace --all-targets -- -D warnings && \
   cargo test --workspace -- --test-threads=4 && cargo fmt --all -- --check && \
   cargo check -p pi-coding-agent --no-default-features'
```

Clippy pedantic lints are errors (`-D warnings`); do not silence them to get
green. After the bump, confirm `pi --version` / the binary's reported version
matches the Cargo version before tagging.

## 5. Publishing the release

### 5.1 Preferred: tag-triggered workflow (after `WIRING.md` §2 is merged)

The proposed `build-release-assets` + `publish-release` jobs add a `v*` tag
trigger, build all four targets, emit one `<asset>.sha256` per binary, and
attach everything to the Release with generated notes. The coordinator's job
is then:

1. push the annotated tag (approval required — see `WIRING.md` §3);
2. watch the workflow: `gh run list --branch v0.1.0 --limit 5` then
   `gh run watch <run-id> --exit-status`;
3. confirm the Release exists and has **eight** assets (four binaries + four
   `.sha256` files);
4. edit the Release notes if the generated ones need context (approval not
   needed for wording, but announce the release only after user sign-off).

### 5.2 Manual fallback (only if the workflow is not merged)

With explicit user approval, set the version, gate, and build each target
locally, then create the release and attach the files in one command:

```sh
gh release create v0.1.0 \
  dist/pi-linux-x86_64 dist/pi-linux-x86_64.sha256 \
  dist/pi-linux-aarch64 dist/pi-linux-aarch64.sha256 \
  dist/pi-darwin-x86_64 dist/pi-darwin-x86_64.sha256 \
  dist/pi-darwin-aarch64 dist/pi-darwin-aarch64.sha256 \
  --title "pi-rs v0.1.0" --generate-notes
```

Generate each checksum in the directory containing the binary, so the file
contains just the basename (this is the format the installer parses):

```sh
cd dist
sha256sum pi-linux-x86_64 > pi-linux-x86_64.sha256       # Linux
shasum -a 256 pi-darwin-aarch64 > pi-darwin-aarch64.sha256  # macOS/BSD
```

`gh release upload v0.1.0 <files...>` attaches additional assets to an
existing release. Never commit release binaries — they are build artifacts.

## 6. Installer contract

`scripts/install.sh` expects, for release tag `TAG`:

| Asset | Purpose |
|---|---|
| `pi-linux-x86_64` | binary, Linux x86-64 |
| `pi-linux-aarch64` | binary, Linux ARM64 |
| `pi-darwin-x86_64` | binary, macOS Intel |
| `pi-darwin-aarch64` | binary, macOS Apple Silicon |
| `<binary asset>.sha256` | one checksum file per binary, format `<sha>  <basename>` (a single `SHA256SUMS` with the same lines is also accepted as a fallback) |

The installer maps `uname -s`/`uname -m` to that table, downloads the binary
and its checksum, verifies SHA-256 (with `sha256sum` or `shasum -a 256`), and
only then copies it to `$PI_INSTALL_DIR/pi` (default `~/.local/bin/pi`). It
never pipes downloads to a shell, never writes outside the prefix (apart from
a cleaned-up `TMPDIR` scratch dir), and uses `sudo` only with `--sudo`.

## 7. Verify a release locally with the installer

The repo is public, so no token is needed. Download the script as a *file*
(the piped one-liner is also supported):

```sh
curl -fsSLO https://raw.githubusercontent.com/hakergeniusz/pi-rs/main/scripts/install.sh
sh ./install.sh --help                    # options/usage
sh ./install.sh --version                 # installer version
DEST=$(mktemp -d)
sh ./install.sh --prefix "$DEST" v0.1.0
"$DEST/pi" --help
"$DEST/pi" --version                      # must report 0.1.0
```

Expected: a `checksum OK` line, then the install path and next steps. Re-run
with `--force` to replace an existing install in the same prefix. To check the
checksum independently of the installer:

```sh
cd "$DEST" && sha256sum -c pi-linux-x86_64.sha256   # or shasum -a 256 -c ...
```

A mismatch, a 404, or a token error must leave the prefix untouched. After
verifying, remove the scratch dir (use `trash` on the operator's workstation).

## 8. Post-release

- Append a dated entry to `HANDOFF.md` (release cut, tag, CI run ID, asset
  list) and update the `README.md` status line if the gate changed it.
- Confirm CI's `main` run is still green after the version commit.
- ff-merge the release topic branch to `main`, delete the branch, push — each
  per `AGENTS.md` and with user approval.
- Deleting a bad tag/Release or re-cutting `v0.1.0` is a destructive/shared
  history operation: ask the user first.
